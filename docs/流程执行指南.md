# 假装社区执行流程指南

本指南定义了“产品设计 → UI 设计 → 开发实现 → 测试验证 → 验收交付”的标准流程，帮助团队按项目约定顺畅衔接。

## 角色责任映射

- 产品经理（product）：负责 `docs/prd-*.md`，定义需求和验收标准
- UI 设计师（ui）：负责 `docs/ui-*.md`，设计界面与交互方案
- 开发工程师（dev）：负责代码实现，并输出 `report.json`
- 测试工程师（test）：负责测试验证，并产出 `tests/` 测试代码
- 调度者/Orchestrator：负责生成 `.claude/packets/*.json` 并记录 `.claude/events/events.jsonl`

## 1. 目标

让所有角色共享统一执行流程，避免跨角色责任模糊，保证交付文档清晰、任务可追踪、验收标准明确。

## 2. 角色与交付物

### 产品经理
- 产物：`docs/prd-*.md`
- 作用：定义功能目标、用户价值、用户故事、功能细节、交互流程、验收标准
- 典型输出：`docs/prd-帖子发布与展示.md`

### UI 设计师
- 产物：`docs/ui-*.md`
- 作用：基于 PRD 输出页面结构、组件布局、交互状态、响应式方案、Tailwind 可实现代码片段
- 典型输出：`docs/ui-帖子发布与展示.md`

### 开发工程师
- 产物：`app/`、`components/`、`lib/`、`types/` 代码，`report.json`
- 作用：实现产品需求、落地 UI 设计、保证功能可用、维护代码质量

### 测试工程师
- 产物：`tests/` 中的测试代码，`report.json`
- 作用：根据 PRD 验收标准设计测试用例，验证功能、回归检查质量门禁

### 调度与验收
- 产物：`.claude/packets/*.json`、`.claude/events/events.jsonl`
- 作用：结构化任务派发、记录决策、执行验收判断

## 3. 标准执行步骤

### 3.1 产品需求阶段
1. 写出 `docs/prd-*.md`，包含完整 PRD 结构。
2. 与业务方确认需求目标、优先级、范围边界。
3. 明确验收标准，最好用 checkbox 形式。

### 3.2 UI 设计阶段
1. 读取已批准的 PRD。
2. 输出 `docs/ui-*.md`，包含线框图、组件规范和 Tailwind 代码片段。
3. 明确移动端与桌面端响应式行为。
4. 与产品确认设计是否满足用户故事与交互流程。

### 3.3 开发实现阶段
1. 拆解功能点，按 PRD 和 UI 文档做任务分解。
2. 实现最小可用功能，优先完成 P0。
3. 对用户输入添加 Zod 校验，保持类型安全。
4. 提交代码并记录修改文件、测试结果、变更摘要到 `report.json`。

### 3.4 测试验证阶段
1. 从 PRD 的验收标准生成测试用例。
2. 在 `tests/` 中编写单元/集成/E2E 测试。
3. 验证核心流程：发帖、展示、评论、点赞、登录等。
4. 输出测试结论与缺陷列表到 `report.json`。

### 3.5 验收与交付
1. 按 PRD checkbox 逐项确认功能是否达标。
2. 检查 UI 是否与 `docs/ui-*.md` 对齐。
3. 确保 `pnpm lint`、`pnpm typecheck`、`pnpm test` 的结果通过。
4. 记录验收结果到 `.claude/events/events.jsonl`。

## 4. 交付规范与文件命名

- 产品需求：`docs/prd-功能名.md`
- UI 设计：`docs/ui-功能名.md`
- 过程指南：`docs/流程执行指南.md`
- Packet：`.claude/packets/pkt-YYYYMMDD-xxxx.json`
- 测试：`tests/` 下按 `unit/`、`integration/`、`e2e/` 分类

## 5. 典型流程示例

1. 产品：生成 `docs/prd-帖子发布与展示.md`
2. UI：生成 `docs/ui-帖子发布与展示.md`
3. 开发：按文档实现帖子发布页、帖子列表、帖子详情、评论、点赞
4. 测试：覆盖发帖、列表展示、交互和未登录权限场景
5. 验收：确认所有 PRD checkbox 勾选完成，生成 Barrier 结果
